# Kotlin: Desktop → Android

Минимальный, но достаточный маршрут для человека с опытом Java Core, чтобы написать
клиент-серверное приложение с UI из стандартных компонентов.

---

## Исходные предпосылки

Предполагается, что уже есть:

- Java Core (ООП, коллекции, generics, исключения, потоки на уровне `Thread`/`Executor`)
- Git
- XML, JSON как форматы
- Понимание HTTP: методы GET / POST / PUT / DELETE, заголовки, тело запроса

Предполагается, что **нет**: Kotlin, корутин, декларативного UI, современного Android.

---

## Почему сначала desktop

Desktop-этап здесь не «для разминки». На нём используется **тот же стек**, что потом
на Android, но без эмулятора, lifecycle, permissions, манифеста и Android-специфичного
Gradle. Цикл «правка → запуск» — секунды, а не минута. Любая ошибка на этом этапе
относится к языку или к библиотеке, а не к платформе.

Второе: если начать сразу с Android, придётся одновременно учить Kotlin + корутины +
Compose + Android SDK. Четыре незнакомых слоя сразу — это и есть главная причина, по
которой переход «застревает».

---

## Стек: выучить один раз, не переучиваться

| Слой | Инструмент | Desktop | Android |
|---|---|:---:|:---:|
| Язык | Kotlin | ✅ | ✅ |
| Асинхронность | coroutines + Flow | ✅ | ✅ |
| Сеть | Ktor Client | ✅ | ✅ |
| JSON | kotlinx.serialization | ✅ | ✅ |
| UI | Compose (Desktop / Android) | ✅ | ✅ |
| Сборка | Gradle Kotlin DSL | ✅ | ✅ |

Что при переходе на Android переносится, а что меняется:

| Слой | Судьба при переходе |
|---|---|
| `domain/` (модели, интерфейсы репозиториев, `ApiResult`) | дословно |
| `data/` (API, DTO, мапперы, репозитории) | дословно, кроме одной строки — движка Ktor (`CIO` → `OkHttp`) |
| Модели экранов (`StateFlow`, логика) | одна строка: свой `scope` → `viewModelScope` |
| `@Composable`-экраны | `collectAsState()` → `collectAsStateWithLifecycle()` |
| Точка входа | `application { Window { } }` → `ComponentActivity` |
| Роутинг | `when` по состоянию → `NavHost` |
| Сборка | добавляются манифест, `targetSdk`, разрешения |

Полный список различий — в таблице на [этапе 7](07-android-basics.md). Смысл
desktop-этапа в том, что переписывать приходится только два верхних слоя из семи,
а логика приложения переезжает как есть.

Этапы 3 и 4 формально независимы друг от друга и могут идти в любом порядке — но

корутинах, и попытка учить их одновременно обычно заканчивается тем, что непонятно
ни то, ни другое.

## Целевая архитектура (одна и та же на обеих платформах)

```
┌─────────────────────────────────────────┐
│  UI (@Composable)                       │
│  читает StateFlow, отдаёт колбэки       │
└───────────────┬─────────────────────────┘
                │ collectAsState()
                ▼
┌─────────────────────────────────────────┐
│  ViewModel                              │
│  MutableStateFlow<UiState>              │
│  область корутин: своя на desktop,      │
│  viewModelScope на Android              │
└───────────────┬─────────────────────────┘
                │ suspend fun
                ▼
┌─────────────────────────────────────────┐
│  Repository                             │
│  DTO → domain-модель, обработка ошибок  │
└───────────────┬─────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────┐
│  Ktor Client + kotlinx.serialization    │
└─────────────────────────────────────────┘
```

Три слоя — это минимум, который имеет смысл. Меньше — и логика запроса переедет в UI.
Больше (use cases, отдельные data source, mapper-классы) — на этом маршруте
преждевременно.

## Что сознательно не входит в маршрут

Список нужен, чтобы не расползаться. Всё перечисленное — полезно, но **не сейчас**:

- Kotlin Multiplatform, Compose Multiplatform
- RxJava, Dagger напрямую
- MVI-фреймворки (Orbit, MVIKotlin, Decompose)
- Написание своих Gradle-плагинов, KSP, кодогенерация
- WorkManager, Paging 3, Services, CameraX
- Анимации Compose, `Canvas`, кастомный layout
- Продвинутый Kotlin: `inline`/`reified`, делегаты свойств, DSL-билдеры,
  перегрузка операторов, `value class`

Две темы вынесены не в «никогда», а в приложения: [Retrofit](appendix-retrofit.md)
и [тестирование](appendix-testing.md).

## Как пользоваться этими документами

Файлы этапов бывают двух видов, и устроены они по-разному.

**Теоретические этапы** ([1](01-language.md), [2](02-coroutines.md),
[2b](02b-flow.md), [3](03-network-json.md), [4](04-compose-desktop.md),
[7](07-android-basics.md)) — одинаковый шаблон:

- **Цель** — что должно быть в голове по итогу
- **Темы** — что учить, с пояснением «зачем это здесь»
- **Не учить на этом этапе** — что отложить, чтобы не тратить время
- **Упражнения** — мелкие задачи, по 15–40 минут
- **Чекпоинт** — критерий «этап пройден», проверяемый, а не «прочитал»
- **Ссылки** — официальная документация по темам этапа

**Интеграционные этапы** ([5](05-desktop-project.md),
[8](08-android-project.md)) вместо «Тем» содержат постановку задачи, структуру
проекта, ключевые куски кода, порядок работы по вечерам и разбор типовых проблем.
Отдельно стоят [этап 0](00-environment.md) (только настройка) и
[этап 6](06-android-changes.md) (только чтение, без кода).

**Приложения** — не входят в маршрут и читаются по потребности:
[Retrofit](appendix-retrofit.md) нужен, чтобы читать и править существующие
Android-проекты, где почти всегда стоит он, а не Ktor;
[Тестирование](appendix-testing.md) — точка входа туда, куда маршрут
последовательно откладывает: `runTest`, Turbine, MockEngine.

**[Глоссарий](glossary.md)** — не этап, а справочная страница: ключевые слова
Kotlin, символы (`?.`, `?:`, `!!`, `::`, `->`), термины корутин, Flow, Compose,
Android и Gradle, каждый с пояснением в одну-две строки. Читать подряд не нужно;
это место, куда возвращаются, встретив незнакомое слово. Документы рассчитаны на
человека, который Kotlin не знает вообще, поэтому всё служебное объясняется по
ходу — но если что-то встретилось раньше, чем объяснено, оно есть в глоссарии.

Главное правило: **не читать подряд**. На каждую тему — сразу мелкая задача в
консоли. Kotlin читается легко и создаёт ложное ощущение понимания; оно рассыпается
при первой же попытке написать самому.

## Точки, где стоит остановиться и подумать

- **Конец этапа 1.** Если `sealed class` + `when` не воспринимаются как естественный
  способ описать «результат операции» — вернуться к этой теме. Дальше она будет везде.
- **Конец этапа 2.** Если непонятно, почему область корутин отменяет всё внутри себя
  сама, — вернуться к структурной конкурентности. Это ядро всей модели, и без него
  этап 2b будет непонятен.
- **Конец этапа 2b.** Если «холодный» и «горячий» поток не различаются на уровне
  интуиции — вернуться. На этом стоит всё состояние UI дальше.
- **Конец этапа 4.** Если state hoisting кажется лишним усложнением — вернуться.
  Без него Compose-код разваливается на 300 строках.

## Альтернативная ветка (если Compose не подходит)

Compose — единственный вариант UI, который переносится с desktop на Android без
переписывания. Но если по каким-то причинам нужен классический путь:

- Desktop: **Swing** — знакомо, работает, но не переносится совсем
- Android: **XML + Views + ViewBinding + RecyclerView**

В этом случае этапы 0–3 остаются без изменений, а этапы 4, 5, 7, 8 меняются
полностью. Практический компромисс: пройти маршрут как есть на Compose, а
XML/Views добрать одним вечером в конце — этого хватает, чтобы читать и править
существующий код команды.

См. раздел «Если проект команды на XML» в [07-android-basics.md](07-android-basics.md).
