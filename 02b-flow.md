# Этап 2b. Flow

**Время:** 2 вечера
**Предыдущий:** [02. Корутины](02-coroutines.md) · **Следующий:** [03. Сеть и JSON](03-network-json.md) · [Обзор](README.md)

## Цель

Понимать `Flow` не как «ещё одну реактивную библиотеку», а как естественное
продолжение `suspend`-функций: одно значение → много значений.

На этом этапе строится всё, что дальше: обновление UI, данные из БД, поиск с
задержкой, состояние экрана. Пропустить его нельзя — дальше он будет везде.

По-прежнему только консоль.

---

## Что нужно знать заранее

С [этапа 2](02-coroutines.md): `suspend fun`, `CoroutineScope`, `launch`,

уложилось, Flow поверх непонятых корутин учить бессмысленно — он весь на них
построен.

## Темы

### 2b.1. Что это такое

`suspend`-функция возвращает **одно** значение и завершается. `Flow` отдаёт **много**
значений во времени. Если разложить по двум осям, видно, какую клетку он занимает:

| | одно значение | много значений |
|---|---|---|
| **синхронно** | обычный `return` | `List`, `Sequence` |
| **асинхронно** | `suspend fun` | **`Flow`** |

Ближайший знакомый аналог из Java — `java.util.stream.Stream`: ленивая цепочка
операций, которая ничего не делает до терминальной операции. `Flow` — то же самое,
но не блокирует поток и умеет ждать.

> Отдельно предупреждение на будущее: в Java 9 появился класс
> `java.util.concurrent.Flow` — это **не то же самое**, а всего лишь четыре
> интерфейса спецификации Reactive Streams, без единого оператора. Совпадение имён
> случайное и путает. По духу Kotlin `Flow` ближе к `java.util.stream.Stream`.

### 2b.2. Минимальный пример

```kotlin
// производитель: функция, возвращающая поток целых чисел
fun numbers(): Flow<Int> = flow {
    for (i in 1..3) {
        delay(300)      // ждём, не занимая поток
        emit(i)         // отдаём значение потребителю
    }
}

// потребитель: обязательно внутри корутины, потому что collect — suspend-функция
scope.launch {
    numbers().collect { value ->
        println(value)  // 1, потом 2, потом 3 — с интервалом 300 мс
    }
}
```

Разбор служебных слов, которые здесь появились:

- **`flow { }`** — не ключевое слово языка, а обычная функция из библиотеки,
  принимающая лямбду. Она эту лямбду **сохраняет**, а не выполняет
- **`emit(value)`** — «отдать значение». Доступна внутри `flow { }` без всякого
  объявления, потому что лямбда объявлена как *функция-расширение с получателем*
  (см. ниже)
- **`collect { }`** — терминальная операция: запускает всю цепочку. Это
  `suspend`-функция, поэтому вызывается только из корутины
- **`value ->`** — имя параметра лямбды. Если параметр один, имя можно не писать и
  обращаться к нему как `it`: `collect { println(it) }`

### 2b.3. Холодность — главное свойство

`numbers()` не выполняет ничего. Он создаёт объект, внутри которого лежит лямбда,
и возвращает его. Ни `delay`, ни `emit` не срабатывают.

```kotlin
val f = numbers()          // 0 мс, ничего не произошло
f.collect { println(it) }  // вот теперь пошла работа: 900 мс
f.collect { println(it) }  // и ещё раз, с нуля: ещё 900 мс
```

Это и называется **холодный** поток: он как рецепт, а не как кастрюля на огне.
Каждый `collect` — новое независимое выполнение.

Практическое следствие: если внутри `flow { }` стоит сетевой запрос, два `collect`
дадут два запроса. Способ этого избежать — `stateIn` / `shareIn`, о них ниже.

### 2b.4. Как это устроено внутри

Полезно один раз посмотреть, потому что после этого исчезает ощущение магии.
Оба интерфейса — по одному методу:

```kotlin
interface Flow<out T> {
    suspend fun collect(collector: FlowCollector<T>)
}

interface FlowCollector<in T> {
    suspend fun emit(value: T)
}
```

И всё. Никакого внутреннего движка. `flow { }` просто оборачивает лямбду в объект,
реализующий `Flow`, и в момент `collect` передаёт ей коллектор.

Если убрать корутины, на Java это выглядело бы буквально так:

```java
interface FlowCollector<T> { void emit(T value); }
interface Flow<T>          { void collect(FlowCollector<T> collector); }

Flow<Integer> numbers() {
    return collector -> {                 // ← лямбду ВЕРНУЛИ, не выполнили
        for (int i = 1; i <= 3; i++) {
            sleep(300);
            collector.emit(i);
        }
    };
}
```

То есть `Flow<T>` — это по сути `Consumer<FlowCollector<T>>`: объект, умеющий
принять приёмник и скормить ему значения. Пока приёмника нет, эмитить некуда —
отсюда холодность.

**Почему `emit` доступна без получателя.** Тип лямбды в `flow { }` —
`suspend FlowCollector<T>.() -> Unit`. Точка перед круглыми скобками означает
*функцию-расширение*: внутри лямбды `this` — это коллектор, а `emit(i)` —
сокращение от `this.emit(i)`. Тот же приём используется в `apply { }` из
[этапа 1](01-language.md), где внутри блока доступны поля настраиваемого объекта.

### 2b.5. Что происходит при `collect`

Ключевой момент, который ломает интуицию: **`emit` не кладёт значение в очередь и
не отправляет его в другой поток.** Это обычный вызов кода потребителя. В момент
`println(1)` стек выглядит так:

```
лямбда потребителя { println(it) }
  ← emit(1)
    ← тело flow { }
      ← collect()
        ← launch { }
```

Производитель физически ждёт, пока потребитель обработает значение. Отсюда
**backpressure** («обратное давление») получается бесплатно: медленный потребитель
автоматически тормозит быстрого производителя, потому что `emit` — `suspend`-функция
и приостанавливается до возврата.

В RxJava для этого нужно было выбирать стратегию (`BUFFER`, `DROP`, `LATEST`), в
чистой Java — `BlockingQueue` с блокировкой потока. Здесь — само, и без занятого
потока.

### 2b.6. Операторы

Оператор — функция, которая берёт `Flow` и возвращает новый `Flow`. Цепочка
операторов ничего не выполняет до `collect`.

```kotlin
numbers()
    .map { it * 10 }        // преобразовать каждое значение
    .filter { it > 10 }     // пропустить только подходящие
    .onEach { log(it) }     // побочное действие, значение не меняется
    .collect { print(it) }  // ← только здесь всё запускается
```

Минимально нужный набор:

| Оператор | Что делает |
|---|---|
| `map` | преобразовать значение |
| `filter` | пропустить подходящие |
| `take(n)` | взять первые n и закрыть поток |
| `onEach` | сделать что-то с каждым, не меняя его |
| `onStart` / `onCompletion` | код до первого значения / после последнего |
| `catch` | перехватить ошибку **выше** по цепочке |
| `retry(n)` | перезапустить upstream при ошибке |
| `debounce(ms)` | пропустить значение, только если после него была пауза |
| `distinctUntilChanged` | не пропускать значение, равное предыдущему |
| `flatMapLatest` | на новое значение отменить обработку предыдущего |
| `combine` | собрать несколько потоков в один по последним значениям |
| `zip` | объединить строго парами |

**Слова `upstream` и `downstream`** встречаются постоянно: upstream — всё, что
*выше* оператора по цепочке (ближе к производителю), downstream — всё, что *ниже*
(ближе к `collect`). `catch` ловит ошибки только upstream — это важно, потому что
ошибку в самом `collect { }` он не перехватит.

Каждый оператор — это просто ещё один `flow { }`, обёрнутый вокруг предыдущего:

```kotlin
fun <T, R> Flow<T>.map(transform: suspend (T) -> R): Flow<R> = flow {
    collect { value ->            // подписались на upstream
        emit(transform(value))    // отдали в downstream
    }
}
```

Поэтому вся цепочка — одна корутина и один вызов, без промежуточных очередей и
объектов-подписок. По этой причине Flow заметно дешевле RxJava по аллокациям.

**Второй способ запустить цепочку — `launchIn`.** `collect` приостанавливает текущую
корутину до конца потока, и это не всегда удобно: если нужно просто «подписаться и
идти дальше», используют `onEach` + `launchIn`:

```kotlin
// эти две записи делают одно и то же
scope.launch {
    someFlow.collect { handle(it) }
}

someFlow
    .onEach { handle(it) }
    .launchIn(scope)          // ← сам создаёт корутину в указанной области
```

`launchIn` возвращает `Job`, так что подписку можно отменить отдельно от всей
области. Вариант с `launchIn` читается лучше, когда подписок несколько: три
`collect` подряд в одной корутине не сработают — первый заблокирует остальные, —
а три `launchIn` работают параллельно.

### 2b.7. Смена потока

```kotlin
flow { emit(loadFromDisk()) }
    .map { it.uppercase() }
    .flowOn(Dispatchers.IO)     // всё, что ВЫШЕ, уходит на IO-пул
    .collect { updateUi(it) }   // выполняется там, где вызван collect
```

`flowOn` задаёт контекст **upstream**. Аналога `observeOn` из RxJava нет и не нужно:
потребитель работает в том контексте, в котором вызван `collect`. Собрал внутри
корутины на `Dispatchers.Main` — значит, `collect` в главном потоке.

### 2b.8. Обработка ошибок

```kotlin
numbers()
    .retry(retries = 2) { e ->
        delay(300)
        e is IOException      // true = повторить, false = пропустить дальше
    }
    .catch { e ->
        emit(-1)              // fallback-значение вместо падения
    }
    .collect { println(it) }
```

Две особенности, о которые спотыкаются:

- `retry` перезапускает **весь** upstream с нуля, а уже отданные значения никуда не
  исчезают. Если поток успел отдать `1` и упал, после повтора `1` придёт снова.
  Опасно, если между retry и collect есть побочные эффекты вроде записи в БД
- `try/catch` **вокруг** `emit` внутри `flow { }` поймает исключение из кода
  потребителя, а не своё — потому что стек общий (см. выше). Для ошибок производителя
  используется оператор `catch`

### 2b.9. Горячие потоки: `StateFlow` и `SharedFlow`

Холодный Flow не подходит для состояния экрана: нужно, чтобы значение было всегда,
а не пересчитывалось для каждого подписчика. Для этого есть **горячие** потоки —
они существуют независимо от того, слушает их кто-нибудь или нет.

```kotlin
class UsersModel {
    // приватный изменяемый — только внутри класса
    private val _users = MutableStateFlow<List<User>>(emptyList())
    // публичный только для чтения — наружу
    val users: StateFlow<List<User>> = _users.asStateFlow()

    fun add(user: User) {
        _users.update { it + user }      // атомарное обновление
    }
}
```

Служебные детали этого шаблона, он встретится десятки раз:

- **`MutableStateFlow`** можно менять, **`StateFlow`** — только читать
- **подчёркивание в `_users`** — не синтаксис языка, а соглашение: так помечают
  приватное изменяемое поле, у которого есть публичный неизменяемый двойник
- **`asStateFlow()`** возвращает тот же объект, но под типом только для чтения,
  чтобы снаружи нельзя было присвоить значение
- **`update { }`** читает текущее значение и записывает новое одной атомарной
  операцией; `_users.value = ...` тоже работает, но небезопасно, если обновления
  идут из разных корутин

Чем `StateFlow` отличается от холодного Flow:

| | холодный `Flow` | `StateFlow` | `SharedFlow` |
|---|---|---|---|
| Есть значение всегда | нет | да | нет |
| Новый подписчик получает | всё с нуля | текущее значение | ничего (по умолчанию) |
| Дубликаты | пропускает | отсекает (`distinctUntilChanged` встроен) | пропускает |
| Для чего | загрузка данных | состояние экрана | одноразовые события |

`StateFlow` — прямая замена `LiveData` из Android. `SharedFlow` — шина событий
(«показать сообщение», «перейти на другой экран»): у него нет начального значения,
поэтому событие не покажется повторно при новой подписке.

### 2b.10. `stateIn` и `shareIn` — из холодного в горячее

Это то, что связывает два мира: данные приходят холодным потоком (из БД, из сети),
а UI нужно горячее состояние.

```kotlin
val users: StateFlow<List<User>> = repository.observeUsers()   // холодный
    .stateIn(
        scope = scope,                                          // кто владеет подпиской
        started = SharingStarted.WhileSubscribed(5_000),        // когда работать
        initialValue = emptyList()                              // что отдать до первых данных
    )
```

Что даёт: **один запуск на всех подписчиков** вместо перезапуска на каждого.

`started` определяет политику, и вариантов три:

| Значение | Поведение |
|---|---|
| `WhileSubscribed()` | работает, пока есть подписчики; без них останавливается сразу |
| `WhileSubscribed(5_000)` | то же, но с задержкой 5 с — переживает краткий перерыв в подписке |
| `Eagerly` / `Lazily` | стартует сразу / при первом подписчике и **не останавливается** |

Задержка в `WhileSubscribed(5_000)` кажется мелочью, но на Android именно она
спасает от лишней работы при повороте экрана. Подробно — на
[этапе 8](08-android-project.md).

### 2b.11. Чего делать нельзя

**Эмитить из другой корутины.** `emit` синхронно вызывает downstream, а downstream
обязан выполняться в контексте вызова `collect`:

```kotlin
flow {
    launch { emit(1) }                        // ошибка
    withContext(Dispatchers.IO) { emit(1) }   // IllegalStateException в рантайме
}
```

Сообщение будет: *«Flow invariant is violated: emission from another coroutine
context»*. Контекст меняется только `flowOn` **снаружи** цепочки.

**Полагаться на однократность побочных эффектов.** Тело холодного Flow
перезапускается для каждого подписчика. Нужен один запуск — `stateIn` / `shareIn`.

**Захватывать изменяемое внешнее состояние в лямбде.** Лямбда живёт долго и
запускается многократно; ссылка на объект UI или счётчик-поле дадут неожиданное
поведение и утечку.

### 2b.12. Соответствия с Java

| Java / старый Android | Kotlin |
|---|---|
| `CompletableFuture<T>`, `Single<T>` | `suspend fun(): T` |
| `Stream<T>` (ленивый) | `Flow<T>` (ленивый, асинхронный) |
| `Observable` / `Flowable` (RxJava) | `Flow<T>` |
| колбэк-интерфейс с несколькими вызовами | `Flow<T>` |
| поле + `List<Listener>`, `LiveData` | `StateFlow<T>` |
| EventBus, `PropertyChangeSupport` | `SharedFlow<T>` |
| `BlockingQueue.put()` | `emit()` |
| `subscribeOn` | `flowOn` |
| `observeOn` | не нужен: контекст задаёт `collect` |
| `CompositeDisposable.clear()` | отмена области корутин |

Главное отличие от RxJava: там **всё** приходилось выражать операторами — нельзя
было написать обычный цикл или `if` посередине цепочки. `Flow` работает поверх
`suspend`-функций, поэтому внутри `flow { }` и внутри любого оператора пишется
обычный последовательный код. Реактивность здесь только снаружи, в виде цепочки;
внутри — привычная императивная логика.

### 2b.13. Итоговый шаблон: класс с состоянием

Всё, что разобрано выше, сходится в одну конструкцию, которая дальше по маршруту
встретится десятки раз. Это прообраз `ViewModel` из Android — и, как выяснится на
[этапе 7](07-android-basics.md), почти дословно она и есть.

```kotlin
class UsersModel(private val repo: UserRepository) : Closeable {

    // область корутин: своя, потому что на desktop готовой ещё нет
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

    // приватное изменяемое состояние + публичное только для чтения
    private val _state = MutableStateFlow<UiState<List<User>>>(UiState.Loading)
    val state: StateFlow<UiState<List<User>>> = _state.asStateFlow()

    fun load() {
        scope.launch {
            _state.value = UiState.Loading
            _state.value = try {
                UiState.Success(repo.getUsers())
            } catch (e: CancellationException) {
                throw e                                  // отмену не глотаем
            } catch (e: Exception) {
                UiState.Error(e.message ?: "Неизвестная ошибка")
            }
        }
    }

    override fun close() { scope.cancel() }              // отменяет всё разом
}
```

Здесь сходятся все темы двух этапов сразу: своя область корутин и структурная
конкурентность из [этапа 2](02-coroutines.md), `SupervisorJob`, проброс
`CancellationException`, `sealed`-тип `UiState` из [этапа 1](01-language.md) и
шаблон `_state` / `asStateFlow()` отсюда.

Потребитель этого класса — будь то консоль, Compose-экран или тест — знает про него
ровно две вещи: `state` для чтения и методы для действий. Ни корутин, ни
исключений наружу не выходит.

## Не учить на этом этапе

- `Channel`, `produce`, `actor` — почти всегда заменяются `Flow`
- `callbackFlow` / `suspendCancellableCoroutine` — понадобятся при обёртке
  Java-колбэков; вернуться к этому на Android
- `buffer`, `conflate`, `flowOn` с размером буфера — тонкая настройка
  производительности, до реальной нагрузки не нужна
- `SharedFlow` с `replay` и `extraBufferCapacity` — знать, что параметры есть
- `flattenMerge`, `flatMapMerge`, `flatMapConcat` — на маршруте хватает
  `flatMapLatest`
- Тестирование Flow (Turbine) — вынесено в [приложение](appendix-testing.md)
- Реализация своего оператора

## Упражнения

1. **Холодность.** Написать `flow { }` с логом в начале тела. Вызвать функцию,
   ничего не собирая — убедиться, что лога нет. Затем собрать дважды и посчитать,
   сколько раз выполнилось тело.
2. **Стек вызовов.** В `collect { }` поставить `Thread.dumpStack()` и посмотреть,
   что тело `flow { }` находится в том же стеке. Это доказательство того, что
   `emit` вызывает потребителя напрямую.
3. **Backpressure.** Производитель эмитит каждые 100 мс, потребитель обрабатывает
   значение 500 мс. Замерить общее время и убедиться, что производитель
   притормаживается, а значения не теряются.
4. **Операторы.** Собрать цепочку `asFlow` → `filter` → `map` → `take(3)` →
   `onEach` → `onCompletion` → `collect` и по логам восстановить порядок вызовов.
5. **`flowOn`.** Печатать `Thread.currentThread().name` в производителе, в `map`
   и в `collect`. Поставить `flowOn(Dispatchers.IO)` и посмотреть, что изменилось.
   Переставить `flowOn` в начало цепочки — объяснить результат.
6. **`catch` и `retry`.** Поток, падающий на второй попытке. Убедиться, что после
   `retry` уже отданные значения приходят повторно.
7. **`debounce`.** Имитировать набор текста: эмитить буквы каждые 100 мс с
   `debounce(300)`. Посчитать, сколько значений дошло.
8. **`flatMapLatest`.** То же, но каждая «буква» запускает «запрос» на 700 мс.
   Убедиться по логам, что незавершённые запросы отменяются.
9. **`StateFlow`.** Два подписчика на один `MutableStateFlow`. Проверить: оба видят
   одно значение; новый подписчик сразу получает текущее; установка того же
   значения не вызывает эмиссии.
10. **`SharedFlow` против `StateFlow`.** Отправить «событие» через оба, затем
    подписаться заново. Увидеть, почему для событий годится только `SharedFlow`.
11. **Итоговое.** Класс `SearchModel`: `StateFlow<String>` для ввода, `debounce`,
    `distinctUntilChanged`, `flatMapLatest` на имитацию запроса, результат в
    `StateFlow<List<String>>`. В `main()` «набрать» слово по букве и по логам
    убедиться, что «запрос» ушёл один раз.
